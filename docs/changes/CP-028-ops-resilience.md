### 1.2 현재 동작
- 처리 예외가 반복되면: 2초마다 예외 → 운영 로그 `EXCEPTION`(where `telegram.notify`) + 콘솔 한 줄. 알림은 대기열(`notification`)에 쌓이기만 하고 텔레그램으로 안 간다. **K11 없음, 위험 확대 계속 허용.**
- 전송 스레드가 죽으면(`_guarded`가 `Exception`을 모두 잡으므로 `BaseException` 계열에서만 가능): 감시 스레드가 긴급 알림 1회(DB·콘솔·운영 로그), 텔레그램 전송 없음, 정지 없음.
- 명령 수신 스레드(`poll_loop`, 64-67행)도 같은 `_guarded`라 반복 예외 시 5초(`ERROR_WAIT`)마다 기록만 한다 — 원격 `/kill` 수신이 조용히 끊길 수 있다.
- `mark_notification`(성공 기록)이 실패하면 예외가 `pump` 밖으로 나가 같은 알림이 다음 회차에 **다시 전송**된다(중복 메시지, 위험 없음 — 참고).

### 1.3 실제 발생 가능성
- 실제 사례: **없음**. `ops-20261004~20261007.jsonl`에 `"kind": "EXCEPTION"` 행 0건(2026-10-07 작성 시점). 1일차 K11은 텔레그램 ReadTimeout(`TelegramError`) 경로로 정상 발동·19초 자동 해제(07-paper-review §3 10:12:50, §7).
- 가능한 원인 [추정]: (1) 다른 프로세스(`scripts/` 운영 도구)가 쓰기 잠금을 5초(`busy_timeout`) 넘게 쥠 → `StorageFailure` — 일시적 (2) 특정 알림 행이 마스킹·형식화에서 예외를 내는 코드 결함 — **영구적**(대기열 맨 앞에서 매번 실패) (3) 스레드 종료 — `_guarded`가 `Exception`을 잡으므로 매우 드묾.
- 영구적 원인(2)이 생기면 사람은 알 길이 없다: 사용자는 평일 장중 부재·텔레그램만 확인 가능(운영 전제).

### 1.4 위험 크기
- **중간**. 주문 경로·게이트는 정상이므로 위험이 직접 커지지는 않지만, 정지·결과 불명·대조 불일치 알림이 사람에게 닿지 않는 상태에서 신규 진입이 계속된다. 이는 D-024(Q-E)가 막으려던 상황("사람이 알 수 없는 상태에서 위험을 늘리지 않는다")과 같다. 채널은 살아 있고 처리만 죽은 경우라 K11 규칙의 문구만 빠져 있는 것으로 본다.

## 2. P2 — 알림 롤백 유실 (F8)

### 2.1 문제 (코드 근거)
| # | 위치 | 내용 |

| 2 | `src/trading_system/storage/repository.py:274-305` | `tx()`는 "중첩 호출은 바깥 트랜잭션에 합쳐진다"(276행): 이미 같은 스레드가 `tx` 안이면 깊이만 늘리고 BEGIN·COMMIT 없이 실행한다(278-284행). 바깥이 예외로 끝나면 `ROLLBACK`(298·301행) — **안쪽에서 쓴 ALERT 행도 함께 사라진다** |

| 4 | `src/trading_system/storage/alerts.py:52-67` | 반복 억제: 같은 (등급·문구·참조) 알림은 60초 창에서 첫 1건만 기록. **억제 창은 롤백과 무관하게 이미 열려 있다** → 재처리로 같은 알림이 다시 나도 억제되어 DB에 안 들어가고, 창이 닫힐 때 "반복 억제 요약" 한 건만 기록된다 |

### 2.2 현재 동작 (경로 예)
- 저장 단위 안에서 알림을 내는 대표 경로(코드 확인):
  - `execution/executor.py:240-246` `process_events`가 `with self._repo.tx(): self.apply_event(...)` → `_apply_fill`의 종결 후 체결(LATE_FILL, 349-351행) 긴급 알림, `_anomaly`(248-253행) → `raise_halt` → `halt/manager.py:84-112` `activate`의 "정지 K4 발동" 알림(이것도 `activate`의 `tx` 안, 112행).
  - `halt/manager.py:88-112` `activate` 자체가 `tx` 안에서 알림을 낸다. 같은 `tx` 안 뒤쪽(예: K5 조건 갱신 113-116행)이 실패하면 정지 행과 알림이 함께 롤백된다.
- 롤백되면: 콘솔·운영 로그에는 "발동"으로 남지만 DB·텔레그램·`status`에는 없다. `process_events`는 남은 통보를 보관했다가 다음 호출에서 다시 반영하므로(241행 설명) 상태 변화 자체는 대부분 재시도로 복구된다. 그러나 문구·참조가 같은 알림(예: LATE_FILL — 참조 = 의도 ID)은 60초 안 재시도에서 **억제**되어 본문 대신 나중의 요약만 텔레그램으로 간다. 참조에 새 ID가 붙는 알림(정지 ID)은 억제되지 않는다.

## 3A. P4 — 장 전 K5 해제가 09:00 첫 정기 대조에만 묶임 (A-074 추가)

### 3A.1 문제 (실측·코드 근거)
- 실측(07-paper-review v0.2 §12A, 2026-10-06·10-07 2일 연속): 07:53 키움 모의 서버가 실시간 연결을 끊음 → K5 → 2초 뒤 실시간 재접속(link:realtime 정상) → 재접속 요청 대조가 같은 시각 조회 실패(kt00018 코드 20) → **그 뒤 대조가 없어** K5가 09:00:01 첫 정기 대조까지 유지.
- 코드: `app/engine.py` `_reconcile_if_due` — 정기 대조는 정규장 안에서만(`in_session`), 장 밖은 요청 대조(`request_reconcile`, 재접속 시 1회)만. 요청 대조가 조회 실패로 끝나면 다시 요청되지 않는다. K5 해제 조건은 "모든 연결 경로 정상 + 그 뒤 대조 일치"(`halt/manager.py` `_k5_missing`).
- 위험: 09:00 첫 정기 대조도 실패하면 1분 주기로 재시도되므로 09:30 전에 풀릴 가능성은 높지만, 장 전 30분 이상의 여유를 쓰지 못한다. 사용자는 평일 장중 부재라 K5가 오래 남으면 그날 매매가 없다.

### 3A.2 대안
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A (권장) | 장 밖에서 **K5가 걸려 있고 그 해제에 대조만 남았을 때**(모든 연결 경로 정상, `reconciled` 미충족) 요청 대조를 **5분 간격, 최대 12회(1시간)** 재시도. 성공(일치)하거나 정규장이 시작되면(정기 대조가 넘겨받음) 중단. 실패 횟수는 메모리(재시작 시 초기화) | 조회 3종 × 최대 12회로 호출 부담 작음. 종료 조건이 명확(CLAUDE.md §8-7) | 서버가 1시간 넘게 거부하면 그대로 09:00 대기 |
| B | 장 밖 정기 대조를 장 전 시간대(예: 08:00~09:00)에도 5분 주기로 | 단순 | K5와 무관하게 조회 증가, 장 전 서버 불안정 구간에 실패 알림 증가 |
| C | 현행 유지 + 문서에 "09:00 첫 대조로 해제" 명시 | 변경 없음 | 위 위험 그대로 |
