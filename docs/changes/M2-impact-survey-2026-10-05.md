## 1. 요약
- 파일 수 기준(패키지 `__init__` 제외 77개, 에이전트 분류): **그대로 재사용 33(43%) / 공통 코드 일반화 필요 30(39%) / M1 전용이라 그대로 두고 M2는 안 씀 14(18%)**, 신규 모듈 약 10개(추정: `broker/binance/` 6, 시세 공급자·24/7 달력 2, 시작 점검 1, 검증 전략 1).
- 일반화 대상 30개에 주문 경로의 큰 파일이 모두 들어 있다(repository 867줄, backtest 630, engine 546, gate 522, reconciler 416, main 416, executor 407). "어댑터만 추가"로 끝나지 않는다. 03 2-M2의 "인터페이스(§5)는 그대로"(03:430)는 코드 판독과 맞지 않는다(§3).
- 가장 큰 설계 결정 3개: **(1) 프로세스·저장 분리 방식**(§4a) — 현재 `var/<mode>/` 하나에 잠금·DB·KILL이 묶여 있다. **(2) 수수료가 받은 자산에서 차감되는 문제**(§4c) — 포지션 수량 정의·대조·dust. 현 코드 그대로면 첫 매수 직후 K4가 예상된다[추정]. **(3) "거래일" 개념의 일반화**(§4d) — 주문 식별 키·일일 손익·세션·일봉 확정이 모두 KST 날짜와 KRX 달력에 묶여 있다.
- M1 PAPER-0가 2026-10-06 시작이므로, 공통 코드 일반화는 M1 운영 코드와 물리적으로 분리된 브랜치·실행 디렉터리에서만 진행하는 것을 권장한다(§7).
- 사용자 결정 필요 10건(§6). 그중 계획 단계(0~5단계 M2 부록) 작성에 차단인 것은 PAPER 환경, 프로세스 구조, 포지션 수량 정의, dust·초기 잔고 처리, 첫 유니버스·주문 유형, 시세 출처다.

### 4c. 수수료가 받은 자산에서 차감되는 문제
사실: "Trading fees are always charged in the asset you receive"(BN §9). 매수하면 기초 자산에서, 매도하면 호가 자산에서 빠진다. 테스트넷 수수료 적용 여부는 미확인(B-U10).
| 안 | 포지션 수량 | 대조 | 장단점 |
|---|---|---|---|
| A | **순 수령**(체결 수량 − 기초 자산 수수료) | 브로커 잔고와 정확 일치 유지 | 02 D-035 원칙 유지. 체결에 수수료·자산 저장 필요(스키마). 주문 수량 ≠ 포지션 증가분 |
| B | 총 체결 | 허용 오차 도입 | 코드 변경 적음. 오차 안에 외부 거래가 숨음, 매도 수량이 잔고를 넘어 거부될 수 있음 |
| C | BNB로 수수료 납부(25% 할인, BN §9) | 기초 자산 차감 없음 | BNB 부족 시 처리 미확인(B-U10), BNB가 관리 대상 자산이 됨 |
- **권장: A.** 청산 수량 = 보유 수량을 stepSize로 내림. 남는 dust는 원장과 대조에는 그대로 두되, "포지션 없음"으로 취급하는 규칙(임계: minQty 미만 또는 평가액이 minNotional 미만)을 따로 정해 소유권 해제(executor.py:403)·L6 종목 수(gate.py:239)·청산 수량 검사(runner.py:114)에 적용한다. 임계와 dust 정리 방법은 사용자 결정(§6-4).
- 테스트넷은 가입 시 여러 자산의 가상 잔고를 준다(BN §2.1). 현 대조는 브로커에만 있는 종목도 불일치로 본다(reconciler.py:259-264). 선택지: (가) 유니버스의 기초 자산과 호가 자산만 대조, 나머지는 기록만 / (나) 시작 기준선을 "수동 소유"(02 D-034)로 반영. (가)는 유니버스 밖 외부 거래를 호가 자산 잔고로만 잡으므로 현금 대조가 함께 필요하다(현재 미구현, reconciler.py:254-318).

### 4g. 인증·시계
- 사실: 서버 처리 조건 `timestamp < serverTime + 1초` 그리고 `serverTime − timestamp ≤ recvWindow`(기본 5000ms, 최대 60000ms), 위반 시 -1021(BN §3). 현재 K6 허용 오차는 절댓값 1초(sntp.py:24).

| 안 | 내용 | 평가 |
|---|---|---|
| A | K6 1초 유지 + 바이낸스 서버 시각(`/api/v3/time`, weight 1) 오차를 시작 점검·주기 점검에 추가 | 권장. 공통 값 불변 |

- 키 유형(사용자 보류, BN §11 Q4): 문서 권장은 Ed25519(BN §3). `userDataStream.subscribe`는 Ed25519 로그온 세션, `.signature` 방식은 "any API Key type"(CHANGELOG 문구, 본문 미대조 — B-U9). ## 7. M1 운영(PAPER-0 진행 중)과의 충돌 방지 원칙
1. **M1 실행본 동결**: PAPER-0·PAPER-1 기간에 M1이 도는 체크아웃(main의 해당 커밋)에는 M2 변경을 넣지 않는다. M1 쪽 변경은 PAPER에서 나온 결함 수정(`fix(T-xxx)`)만.
2. **지금 할 수 있는 것(코드 없음)**: 0~5단계 M2 부록과 공통 본문 CP 작성·승인. 문서 브랜치 `docs/<요약>`(05 D-085) — 현재 `docs/m2-binance-design`.
3. **공통 코드 일반화(§5의 "M1 회귀 시험 필요" 작업)를 넣는 시점 — 권장**: M1 PAPER-0 결과 반영(T-017)이 끝난 뒤 착수. 근거: PAPER-0에서 대조·현금·주문 식별(DP-31·DP-40, K-U 항목)의 M1 쪽 재결정이 예정되어 있어(handoff 로드맵), 같은 코드를 동시에 두 방향으로 고치게 된다. 신규 전용 모듈(T-M2-10·11·14)은 M1 코드를 건드리지 않으므로 계획 승인·구현 시작 지시가 있으면 먼저 진행할 수 있다.
4. **브랜치**: M2 구현은 `feat/T-M2-xx-<요약>`(이름 규칙은 05 M2판에서 확정). 공통 코드 수정은 작업 하나에 하나씩, M1 전체 테스트 통과 후 로컬 커밋. `main` 병합은 사용자 지시로만, **M1 PAPER 실행본의 갱신 여부는 병합과 별개로 사용자가 정한다**(롤백 절차 03 §9).
5. **스키마**: 스키마 버전이 오르는 변경(T-M2-04·05)은 M1 PAPER DB에 마이그레이션이 필요하다. PAPER-1 중간에는 넣지 않는 것을 권장(04 §4.2 기간 연속성). 적용 전 백업은 03 D-060대로.
6. **실행 자원 분리(A1)**: M2는 별도 디렉터리·별도 `.env.paper`·별도 봇. 같은 PC 시계와 회선은 공유하므로 K6·회선 단절은 두 시장에 함께 온다.
7. **승인 경계**: 이 문서는 조사 기록이다. 단계 산출물 승인, M2 구현 시작 지시, 테스트넷 연결 승인, 패키지 설치 승인은 각각 따로 받는다(CLAUDE.md §3).
