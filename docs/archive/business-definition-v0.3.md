## 0-1. 남은 미확인
- 키움 미국주식 모의투자 지원 여부: 3단계 착수 전 공식 확인 (1단계 비차단)
- 바이낸스 Demo Trading 지역 이용 가능 여부, 테스트넷과 실전 체결 차이: 2단계 착수 전 확인
- 세금·약관·해외/크립토 법규: 사용자 확인 항목
- 크립토 24/7 일일 기준 시각, 미국 시장 시간대·서머타임: 각 단계 착수 전 확정
- 리스크 수치 전부(1회 최대 손실, 종목 비중, 총 노출, 일일 손실, 주문 수, 보유 종목 수, 주문 시간대), 정지 유형별 동작, PAPER 합격 기준, 알림 채널, 데이터 출처·비용, 가용성 목표, 로그 보존기간

## 1. 현행 업무와 병목
- [사실] 사용자는 주식·ETF 시장을 분석하며 Python 도구 개발과 백테스트에 관심이 있음.
- [가정] 현재 매매는 사람이 직접 판단·주문. 병목 후보: 규칙 일관성 유지, 장중 상시 감시, 감정 개입, 기록·복기.
- 효과 수치는 근거가 없어 기재하지 않는다.

## 2. 사용 주체와 역할
| 주체 | 역할 |
|---|---|
| 사용자 | 전략·리스크 수치 결정, 단계 승인, LIVE 활성화, 킬 스위치 재개 |
| 시스템 | 데이터 수집, 신호 생성, 리스크 검사, 주문 실행, 대조, 기록, 알림 |
| 증권사·거래소 API | 시세·주문·체결·잔고 제공 (키움, 바이낸스) |
| 개발 에이전트 | 승인 범위 내 문서·코드 작성 (LIVE 실행 권한 없음) |

## 3. 해결할 문제
전략 규칙을 즉흥 판단이나 시스템 오류 없이 일관되게 실행하고, 장애·응답 유실·중복 신호 같은 불확실한 상황에서 위험이 확대되지 않도록 통제한다. 수익 보장은 목표가 아니다.

## 4. 목표와 성공 판정
| ID | 목표 | 판정 방법 |
|---|---|---|
| G-1 | 승인된 규칙대로만 주문 | 리스크 게이트 우회 주문 경로 0건(코드 검토·테스트) |
| G-2 | 불확실 상태에서 위험 비확대 | 응답 유실·단절 시나리오에서 재발주·추가 진입 0건 |
| G-3 | 전략 성과의 검증된 보고 | 비용·슬리피지 가정과 한계를 포함한 백테스트 보고서 |
| G-4 | 실전 전환 전 충분한 모의 검증 | 체크리스트 항목별 충족표(기준 수치는 사용자가 결정) |

## 5. 범위
- 포함(1단계 인도): 국내주식·ETF 키움 모의투자 연동(R-16 첫 어댑터), BACKTEST, 리스크 게이트, 킬 스위치, 주문 상태·대조, 감사 기록, 알림. 2·3단계는 인도 순서 참조.
- 제외: 레버리지·신용·마진·공매도·파생·선물, 수익 보장, 자동 종목 발굴, 세금·법규 판단, 에이전트에 의한 LIVE 실행, 키움 실서버 접속(현재).
- 사람 판단 경계: 종목 선정(스크리닝) 방식은 전략 정의 단계에서 확정. 사람이 선정한 목록은 시스템 입력으로만 취급.

## 6. 사람의 최종 판단 지점
1) 각 단계 산출물 승인 2) 리스크 수치 결정 3) 실전 주문 코드 작성 승인 4) LIVE 실행·활성화 5) 킬 스위치 후 재개 6) 결과 불명 주문이 조회로 해소되지 않을 때의 처리 7) 자동 실행 등록.

## 7. 기능 요구사항
| R-ID | 요구사항 | 인수 기준 (조건 · 입력 · 기대 결과 · 오류 결과) |
|---|---|---|
| R-01 | 실행 모드 통제 | TRADE_MODE가 BACKTEST/PAPER/LIVE일 때만 시작. 누락·오류 값이면 브로커 연결 없이 종료하고 사유 기록. 모드와 브로커 환경 불일치 시 시작 거부 |
| R-02 | 신호 생성 분리 | 전략은 시장 데이터를 입력받아 신호만 출력. 전략 모듈에서 브로커 호출 시 테스트/정적 검사가 실패 |
| R-03 | 단일 주문 경로 | 모든 주문·취소·정정은 중앙 게이트 → 실행기 경유. 우회 호출 경로가 있으면 검증 실패 |
| R-04 | 리스크 게이트 검사 | 킬 스위치, 일일 손실, 종목·총 노출, 미체결 포함 예약 노출, 주문 수, 보유 종목 수, 가격·수량 유효성, 시세 신선도, 거래 시간 중 하나라도 위반하면 거부하고 사유 기록. 동시 신호가 합산 한도를 넘지 않음 |
| R-05 | 중복 주문 방지 | 동일 신호 재전달·재시작·동시 요청 시 주문 1회만 실행. 멱등키 기준은 설계에서 확정 |
| R-06 | 결과 불명 처리 | 타임아웃·응답 유실 시 실패로 단정하지 않고 '결과 불명' 기록. 조회로 해소 전 동일 의도 재발주 금지. 미해소 시 정지·알림·사람 확인 |
| R-07 | 킬 스위치·정지 | 수동/자동 조건 발동 시 신규 진입 차단. 정지 유형별 취소·유지·청산 동작은 사용자 승인 표대로. 재개 조건 충족 전 주문 불가 |
| R-08 | 상태 대조·재시작 복구 | 재시작 직후 주문 불가. 브로커 주문·체결·잔고와 내부 상태를 대조해 일치 확인 후 재개. 불일치 시 정지·알림. 자택 PC 전원·회선 단절 후에도 동일 |
| R-09 | 장애 정책 | API 단절, 시세 지연, 주문 거부, 부분 체결, 인증 만료 각각에 대해 승인된 동작 수행(기본: 추가 주문 없음) |
| R-10 | 백테스트 | 룩어헤드 방지, 비용·슬리피지 가정 명시, 학습/검증 구간 분리. 결과 보고에 한계·과최적화 가능성 포함 |
| R-11 | 감사 로그·마스킹 | 요청ID·신호ID·승인/거부 사유·결과 기록. 앱키·토큰·계좌번호는 로그에 나타나지 않음 |
| R-12 | 비밀정보 관리 | 코드·문서·커밋에 비밀정보 없음. .env 제외, .env.example은 자리표시자만. 바이낸스 API 키에는 출금 권한을 부여하지 않음 [제안, 승인됨] |
| R-13 | 알림 | 거부 급증, 정지, 결과 불명, 대조 불일치, 장애 시 사용자에게 알림 [채널 미확인] |
| R-14 | 시간·시장 캘린더 | 시장별 시간대·휴장·단축장·동시호가·점검 시간에는 승인된 규칙대로만 동작. 1단계는 KRX만 상세화, 크립토 24/7 일일 기준 시각과 미국 시장은 해당 단계 착수 전 확정 |
| R-15 | LIVE 전환 게이트 | 시장·브로커 단위로 판정. 승인 기록 + 사용자 활성화 설정 둘 다 있을 때만 LIVE 허용. 체크리스트 미충족 시 거부. 한 시장의 통과는 다른 시장의 근거가 아님. 에이전트는 LIVE를 켜지 않음 |
| R-16 | 브로커 어댑터 분리 | 키움·바이낸스를 동일 인터페이스로 사용하고 시장별 제약은 어댑터에 격리. 첫 어댑터는 키움 국내 모의. 어댑터 교체로 전략·게이트 코드 변경 없음 |
| R-17 | 전략 등록·버전 관리 | 전략은 이름, 버전, 대상 시장, 필요 데이터, 입력 파라미터, 출력(신호 형식) 명세가 있어야 등록. 명세 누락 시 등록 거부. 게이트 우회 불가. 검증 통과 전 PAPER 투입 불가 |
| R-18 | 상시 가동 | 정전·재부팅·회선 단절 후 대조 완료 전 주문 금지. 프로세스 감시와 알림 제공. 자동 실행 등록은 별도 승인 후에만 구성 |
| R-19 | 전략 설정·파라미터 관리 | 파라미터는 설정 파일로 지정하고 스키마 검증. 누락·형식 오류·허용 범위 밖 값이면 시작 거부. 파라미터 변경은 새 전략 버전으로 관리하고 이전 검증 결과를 승계하지 않음 |
| R-20 | 전략 상태·리스크 한도 | 전략은 초안, 백테스트 통과, PAPER 중, LIVE 후보 상태를 가짐. 상태 전환은 사용자 승인 필요. 전략별 리스크 한도는 계좌 전체 한도를 초과할 수 없음. 주문·손익은 전략 ID·버전별로 기록 |

## 7-1. 전략 관리 변경 (v0.3 승인 반영)
- R-17은 "전략 추가·버전 관리"에서 "전략 등록·버전 관리"로 변경한다.
- R-19, R-20은 신규 요구사항이다.
- 구체적 매매 아이디어는 요구사항이 아니라 docs/00-strategy.md의 전략 후보·승인 문서에서 관리한다.

## 8. 핵심 시나리오
정상: 데이터 수집 → 신호 생성 → 게이트 승인 → (PAPER) 주문 → 체결 확인 → 포지션·손익 기록 → 일일 보고.
실패·예외:
- E-1 주문 전송 후 응답 타임아웃 → 결과 불명 → 주문·체결 조회 → 해소 시 정상 처리, 미해소 시 정지·알림 (R-06)
- E-2 동일 신호 2회 도착 → 두 번째는 중복 거부 (R-05)
- E-3 일일 손실 한도 도달 → 신규 진입 차단, 이후는 승인된 정지 정책 (R-04, R-07)
- E-4 시세 지연 → 신호 무효, 주문 없음 (R-04, R-09)
- E-5 프로세스 재시작·전원 단절 → 대조 완료 전 주문 불가 (R-08, R-18)
- E-6 사용자가 증권사 앱에서 수동 거래 → 대조 불일치 감지, 정지·확인 (R-08)
- E-7 부분 체결 → 잔량은 승인된 규칙대로 (R-09)
- E-8 새 전략 추가 → 명세 누락 시 등록 거부, 검증 전 PAPER 투입 거부 (R-17)
- E-9 전략 파라미터 누락·범위 밖 → 시작 거부, 주문 없음 (R-19)
- E-10 전략별 리스크 한도가 계좌 전체 한도 초과 → 거부, 주문 없음 (R-20)

## 9. 비기능 제약
- 보안: 비밀정보 분리·마스킹, 최소 권한, 자택 PC 접근 통제.
- 신뢰성: 불확실하면 "주문하지 않음"이 기본. 가용성 목표 수치는 사용자 결정.
- 정확성: 금액·수량·호가 단위 규칙 준수, 시간대 명시.
- 외부 제약: 브로커 API 호출 제한·인증·모의/실전 차이는 설계 단계에서 공식 문서로 확인해 기록. 테스트넷·모의 환경은 실전 체결 품질의 근거가 아님.
- 세금·법규·약관: 시스템 판단 대상 아님, 사용자 확인 항목.

## 10. 다음 단계 입력
전략 정의(00-strategy): 전략 유형이 미정이므로 전략 자체가 아니라 전략 정의 형식(입력·판정 시점·조건·행동), 등록 명세, 파라미터 스키마, 상태 전환, 추가 절차, 사람 선정 경계, 실패 국면 가설 틀부터 정의. 스키마 필드와 기술스택은 이 문서에서 확정하지 않음.
