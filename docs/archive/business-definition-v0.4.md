## 1. 현행 업무와 병목
- [사실] 사용자는 주식·ETF 시장을 분석하고, Python 도구 개발과 백테스트에 관심이 있음.
- [가정] 현재는 사람이 직접 판단해 주문함. 병목 후보: 규칙 일관성 유지, 장중 상시 감시, 감정 개입, 기록·복기.
- 효과 수치는 근거가 없어 적지 않는다.

## 2. 사용 주체와 역할
| 주체 | 역할 |

| 시스템 | 데이터 수집, 신호 생성, 리스크 검사, 주문 실행, 대조, 기록, 알림, 일일 보고 [v0.4] |

## 3. 해결할 문제
전략 규칙을 즉흥 판단이나 시스템 오류 없이 일관되게 실행한다. 장애, 응답 유실, 중복 신호 같은 불확실한 상황에서 위험이 커지지 않도록 통제한다. 수익 보장은 목표가 아니다.

## 4. 목표와 성공 판정
| ID | 목표 | 판정 방법 |
|---|---|---|
| G-1 | 승인된 규칙대로만 주문 | 리스크 게이트를 우회하는 주문 경로 0건 (코드 검토·테스트) |
| G-2 | 불확실한 상태에서 위험을 키우지 않음 | 응답 유실·단절 시나리오에서 재발주·추가 진입 0건 |
| G-3 | 전략 성과를 검증해 보고 | 비용·슬리피지 가정과 한계를 포함한 백테스트 보고서 |
| G-4 | 실전 전환 전 충분한 모의 검증 | 체크리스트 항목별 충족표 (기준 수치는 사용자가 결정) |

## 5. 범위
- 포함 (M1 인도): 국내주식·ETF 키움 모의투자 연동(R-16의 첫 어댑터), BACKTEST, 리스크 게이트, 킬 스위치, 주문 상태·대조, 감사 기록, 알림, 일일 보고 [v0.4]. M2·M3는 인도 순서를 따른다.
- 제외: 레버리지·신용·마진·공매도·파생·선물, 수익 보장, 자동 종목 발굴, 세금·법규 판단, 에이전트에 의한 LIVE 실행, 키움 실서버 접속(현재).
- 사람 판단 경계: 종목 선정(스크리닝) 방식은 전략 정의 단계에서 정한다. 사람이 선정한 목록은 시스템에 대한 입력으로만 취급한다.

| R-01 | 실행 모드 통제 | TRADE_MODE가 BACKTEST/PAPER/LIVE일 때만 시작. 값이 없거나 잘못되면 브로커 연결 없이 종료하고 사유를 기록. 모드와 브로커 환경이 다르면 시작 거부. **[v0.4 CP-03] 모드마다 자격정보·저장 데이터·주문 식별 영역을 분리하며, 다른 모드의 자격정보나 저장소를 참조하면 시작 거부** |

| R-14 | 시간·시장 캘린더 | 시장별 시간대·휴장·단축장·동시호가·점검 시간에는 승인된 규칙대로만 동작. **M1**은 KRX만 상세화. 크립토 24/7 일일 기준 시각은 **M2**, 미국 시장은 **M3** 착수 전에 확정 [v0.4: 표기 변경 CP-01] |
| R-15 | LIVE 전환 게이트 | 시장·브로커 단위로 판정. 승인 기록과 사용자 활성화 설정이 둘 다 있을 때만 LIVE 허용. 체크리스트를 충족하지 않으면 거부. 한 시장의 통과는 다른 시장의 근거가 아님. 에이전트는 LIVE를 켜지 않음 |
| R-16 | 브로커 어댑터 분리 | 키움·바이낸스를 같은 인터페이스로 사용하고 시장별 제약은 어댑터 안에 둠. 첫 어댑터는 키움 국내 모의(**M1**). 어댑터를 바꿔도 전략·게이트 코드는 바뀌지 않음 |
| R-17 | 전략 등록·버전 관리 | 전략은 이름, 버전, 대상 시장, 필요 데이터, 입력 파라미터, 출력(신호 형식) 명세가 있어야 등록. 명세가 빠지면 등록 거부. 게이트 우회 불가. 검증을 통과하기 전에는 PAPER 투입 불가 |
| R-18 | 상시 가동 | 정전·재부팅·회선 단절 뒤 대조가 끝나기 전에는 주문 금지. 프로세스 감시와 알림 제공. 자동 실행 등록은 별도 승인 뒤에만 구성 |
| R-19 | 전략 설정·파라미터 관리 | 파라미터는 설정 파일로 지정하고 스키마로 검증. 누락·형식 오류·허용 범위 밖 값이면 시작 거부. 파라미터를 바꾸면 새 전략 버전으로 관리하고 이전 검증 결과를 승계하지 않음 |
| R-20 | 전략 상태·리스크 한도 | 전략은 초안, 백테스트 통과, PAPER 중, LIVE 후보, **[v0.4 CP-06] LIVE 중, 중지, 폐기** 상태를 가짐. **상태는 시장별로 관리.** 상태 전환은 사용자 승인 필요. **중지·폐기 상태에서는 신규 진입 신호를 거부하고, 보유 포지션 처리는 R-07 정지 정책을 따름.** 전략별 리스크 한도는 계좌 전체 한도를 넘을 수 없음. 주문·손익은 전략 ID·버전별로 기록 |

## 8. 핵심 시나리오
정상 흐름: 데이터 수집 → (R-22 품질 검사) → 신호 생성 → 게이트 승인 → (PAPER) 주문 → 체결 확인 → 포지션·손익 기록 → 일일 보고(R-26)

실패·예외:
- E-1 주문 전송 후 응답 타임아웃 → 결과 불명 → 주문·체결 조회 → 해소되면 정상 처리, 해소되지 않으면 정지·알림 (R-06)
- E-2 같은 신호가 2회 도착 → 두 번째는 중복으로 거부 (R-05)
- E-3 일일 손실 한도 도달 → 신규 진입 차단, 이후는 승인된 정지 정책 (R-04, R-07)
- E-4 시세 지연 → 신호 무효, 주문 없음 (R-04, R-09)
- E-5 프로세스 재시작·전원 단절 → 대조가 끝나기 전 주문 불가 (R-08, R-18)
- E-6 사용자가 증권사 앱에서 수동 거래 → 대조 불일치 감지, 정지·확인 (R-08)
- E-7 부분 체결 → 잔량은 승인된 규칙대로 처리 (R-09)
- E-8 새 전략 추가 → 명세가 빠지면 등록 거부, 검증 전 PAPER 투입 거부 (R-17)
- E-9 전략 파라미터 누락·범위 밖 → 시작 거부, 주문 없음 (R-19)
- E-10 전략별 리스크 한도가 계좌 전체 한도를 넘음 → 거부, 주문 없음 (R-20)
- **[v0.4 CP-08]**
- E-11 보유 종목이 거래정지·VI에 들어감 → 신규·증액 거부, 알림, 감액·청산은 U-11 규칙대로 (R-27, R-04)
- E-12 브로커 호출 제한 초과 응답 → 주문 변경 요청은 재시도하지 않음, 조회는 제한된 재시도, 계속되면 정지·알림 (R-09)
- E-13 주문 직전 인증 토큰 만료 → 주문 미전송 상태로 재인증. 전송 뒤 만료로 응답을 받지 못했다면 E-1과 같이 결과 불명 처리 (R-09, R-06)
- E-14 외출 중 사용자가 원격으로 킬 스위치를 발동 → 인증된 운영 요청으로 처리하고 정지 정책 적용, 감사 기록 (R-21, R-07)
- E-15 디스크 가득 참 등으로 상태 저장 실패 → 전송하지 않음, 신규 주문 정지, 알림 (R-25)
- E-16 시스템 시계 오차가 허용치 초과 → 신규 주문 거부, 알림 (R-24)

## 9. 비기능 제약
- 보안: 비밀정보 분리·마스킹, 최소 권한, 자택 PC 접근 통제. [v0.4] 원격 운영 요청 수단은 인증을 거쳐야 하며, 외부에 노출되는 포트는 별도 승인이 필요하다.
- 신뢰성: 불확실하면 "주문하지 않음"이 기본. 가용성 목표 수치는 사용자가 정한다. [v0.4] 상태 저장소는 백업하고 복원 절차를 둔다(R-25).
- 정확성: 금액·수량·호가 단위 규칙 준수, 시간대 명시. [v0.4] 금액·수량에는 이진 부동소수를 쓰지 않는다. 크립토의 소수 수량과 최소 주문 금액 규칙은 거래소 공식 사양을 따른다. 여러 통화에 걸친 계산은 R-23을 따른다.
- 외부 제약: 브로커 API 호출 제한, 인증, 모의/실전 차이는 설계 단계에서 공식 문서로 확인해 `docs/broker-specs/`에 기록한다. 테스트넷·모의 환경은 실전 체결 품질의 근거가 아니다.
- [v0.4] 실행 환경: Windows 11 Pro, Python 3.14.7. 브로커 SDK·라이브러리의 호환성은 3단계에서 확인한다(U-08).
- 세금·법규·약관: 시스템이 판단하지 않는다. 사용자 확인 항목이다.
