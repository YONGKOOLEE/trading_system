## 0. 이 문서의 범위
- 업무정의서 R-01~R-27을 이어받아 인수 기준을 상세화하고, 리스크 정책(한도, 손실률 정의, 요청 유형별 정책, 정지 유형별 동작, 장애 정책)을 정한다.
- **리스크 수치는 사용자가 정한다.** 수치는 문서에 고정하지 않고 설정 파일로 지정한다(D-026). 이 문서는 한도의 정의, 검증 제약, 변경 규칙을 정한다. 에이전트는 선택지와 그 영향만 적는다.
- 운영 기본값(재시도 횟수, 보존 기간 등)은 [제안]으로 적는다. 사용자가 바꿀 수 있다.
- 정하지 않는 것: 데이터 모델(2단계), 컴포넌트·기술(3단계), 백테스트·PAPER 합격 기준(4단계).
- [v0.9 CP-024] 공통 본문을 시장별로 일반화한 문장은 **M1 값·규칙을 "M1:" 또는 2-M1 부록에 그대로 보존**한다. M1 동작은 바뀌지 않는 것이 목표이며, 이 개정 때문에 M1이 쓰는 코드가 바뀌는 행(§2.3.1-3, §2.7 잔고 불일치·부분 체결·대조 주기, §2.12 백업, R-28)은 구현 시 M1 전체 회귀 대상이다(CP-024 §3·§10).

### 2.1 요청 유형 (D-015)
| 요청 유형 | 출처 | 분류 | 설명 |
|---|---|---|---|

#### 2.3.1 한도·시간 설정의 검증과 변경 규칙 (D-026) [제안]
1. **위치**: 비민감 설정 파일(`config/`). 모드별로 분리한다 (R-01). 비밀정보는 넣지 않는다.
2. **기본값 없음**: 값이 하나라도 없거나 형식이 틀리면 시작을 거부한다.
3. **논리 제약** (위반 시 시작·재적재 거부):
   - 비율은 0보다 크다. L1 ≤ L2 ≤ L3, L10 ≤ L3. L3은 레버리지 배수 반영(L9) 때문에 100%를 넘을 수 있으며, 넘으면 시작 시 경고한다.
   - L5, L6은 1 이상 정수. L7은 0보다 큰 금액.
   - [v0.9 CP-024 D-108] 주문 허용 시간대·일일 기준 시각의 제약은 **시장별 규칙**으로 검사한다. 공통: 주문 허용 시간대는 시작 < 종료.
     - M1 (정규장 시장): 주문 허용 시간대는 해당 시장의 정규장 안에 있어야 한다. 일일 기준 시각은 장 시작 전. (v0.8 규칙 그대로)
     - M2 (24/7): 주문 허용 시간대는 거래 세션(매일 UTC 00:00~24:00 한 구간, D-108) 안에 있어야 한다. 일일 기준 시각은 일 경계 UTC 00:00 [결정 A-055]. 정규장·장 시작 전 제약은 적용하지 않는다(2-M2).
4. **적용 시점**:
   - 프로세스 시작 때, 또는 로컬 재적재 명령으로만 읽는다.
   - **더 엄격해지는 변경**은 즉시 적용한다.
   - **완화되는 변경**과 일일 기준 시각 변경은 **다음 일일 기준 시각부터** 적용한다. 손실이 난 날 한도를 풀어 추가 진입하는 것을 막기 위함이다.
5. **원격 변경 불가**: 메신저(D-025)로는 한도를 바꿀 수 없다. 로컬 설정 파일만 허용한다. 급할 때는 킬 스위치를 쓴다.
6. **엄격해져서 현재 보유가 한도를 넘게 되어도** 자동으로 감액·청산하지 않는다. 위험 확대만 거부하고 알림한다 (CLAUDE.md §8-8).
7. **감사**: 변경마다 설정 버전(해시), 변경 전후 값, 적용 시각을 기록한다. 일일 보고(R-26)에 그날 적용된 값을 표시한다.
8. **전략별 한도**: 실행 중 실제 한도는 min(전략 한도, 계좌 한도)이다. 계좌 한도를 낮춰 전략 한도가 더 커지면 알림하고, 다음 시작 때 등록 검증에서 거부한다 (E-10).
9. **LIVE**: LIVE 승인 기록에 한도·시간 설정값(허용 규모)을 포함한다. 실제 설정이 승인값보다 완화되어 있으면 LIVE 시작과 재적재를 거부한다. 완화하려면 재승인한다 (R-15).
10. **모드별 필요 시점**: BACKTEST는 실행마다 설정값을 결과 보고에 기록한다. PAPER는 시작 전에 사용자가 설정한다.

(2) 그 밖의 400(chat not found 등)·401·403·5xx·타임아웃은 연속 실패로 센다(3회 → K11). (3) 전송 제한(429)은 안내된 대기(상한 300초) 동안 보내지 않고, 상한 이내면 연속 실패로 세지 않으며 상한을 넘으면 센다. (4) 4000자를 넘는 알림은 잘라 보낸다. (5) 전송 간격 1초, 한 회차 20건까지(03 D-130). K11 발동·해제 조건은 변경 없음. 근거: 내용 거부 한 건이 대기열을 막아 K11을 영구 유발하거나, 밀린 알림 연속 전송이 전송 제한 → K11이 되는 것을 막기 위함(CP-025 §7.1).

### 2.9 운영 요청과 원격 킬 스위치 (R-21, U-05) (Q-E 결정, 2026-10-01)
- 운영 요청 유형: 취소, 감액, 청산, 킬 스위치 발동, 킬 스위치 재개, 정지 해제(K3·K4·K7 등 사용자 재개 항목).
- 모든 운영 요청은 인증되어야 하고 요청자·시각·내용·결과를 감사 기록한다. 인증 실패는 거부·기록·알림.
- 원격 수단: **메신저 봇 명령** (D-025). 시스템이 메시지를 가져오는 방식이라 외부에 포트를 열지 않는다. 허용 사용자 ID 제한과 명령별 확인 절차를 둔다. 특정 메신저 서비스는 3단계에서 비교·승인.
- 증권사 앱으로 직접 거래하는 것은 시스템 밖의 외부 거래이며 킬 스위치가 아니다 (E-6).
- 선택한 수단의 외부 서비스 연결은 별도 설명·승인 후 3단계에서 설계한다 (CLAUDE.md §5).
- 원격으로 킬 스위치 발동은 항상 허용한다.
- [v0.5 CP-018 D-8] 로컬 kill이 만든 KILL 파일은 로컬에서만 지운다. 원격으로 K1을 재개해도 KILL 파일이 남아 있으면 위험 확대 전송은 계속 막히므로, 재개 응답과 상태 조회에 KILL 파일 존재 여부를 반드시 표시한다. 원격 kill은 KILL 파일을 만들지 않는다.
- [v0.8 CP-023] 텔레그램 메시지가 시스템 시작 시각보다 2분 넘게 오래됐으면(꺼져 있던 동안 보낸 것) `/kill`을 포함해 실행하지 않고 다시 보내라고만 회신한다(감사 기록). 메시지 시각이 없으면 오래된 것으로 보지 않는다.
- [CP-025] 원격 명령을 처리하다 **저장에 실패**하면 그 메시지를 버리지 않고 다음 폴링에서 다시 처리한다. 같은 메시지가 3회 연속 저장에 실패하면 건너뛰고, 허용 채팅에 "접수하지 않음 — 긴급 정지는 PC에서" 회신과 경고 알림을 시도한다. 저장 실패가 아닌 처리 오류는 건너뛰고 기록한다. 형식이 잘못된 메시지는 무시한다. 다시 처리해도 운영 요청은 메시지 ID 멱등키로 1회만 접수된다. 확인 코드는 접수 성공 뒤에만 소비한다(03 D-131·D-132).
- **원격 재개는 K1(수동 킬 스위치)·K2(일일 손실)만 허용**한다. 사람 확인이 필요한 K3·K4·K7과 재시작 대기 K8은 로컬에서만 재개한다 (Q-H).
  - [CP-026] 위 문단을 다음으로 변경: **원격 재개는 K1·K2, 그리고 명령 처리 시점의 새 대조로 조건을 다시 확인한 K4·K8**(03 D-136·D-137)만 허용한다. K3·K7은 로컬에서만 재개한다. 원격 K4 재개는 새 대조가 MATCH이고 열린 불일치 항목이 0건일 때만이며, 대조기가 건 K4만 대상이다(실행기가 건 K4는 로컬). 원격 K8 재개는 새 대조 뒤 §2.11 조건 1~5를 다시 검사해 모두 충족할 때만이다. 여러 계좌가 등록된 경우 전체 범위(계좌 없음) K4·K8은 원격으로 풀지 않는다. 원격 재개에 시간대 제한은 두지 않는다(주문 허용 시간은 게이트가 따로 막는다, D-138). 확인 코드·허용 채팅 ID 절차는 종전과 같다.
- [CP-026] **원격 대조** `/reconcile`: 확인 코드를 거쳐 대조를 1회 실행하고 결과와 열린 불일치 건수를 회신한다. 불일치면 기존 규칙대로 K4 발동·알림(D-139). **원격 요약** `/review`: 조회만(확인 코드 없음, 운영 요청 기록 없음) — 오늘 거래일 체결 건수와 종목·방향·수량, 정지·KILL 파일·결과 불명·불일치 건수, 마지막 대조 결과·시각, 열린 불일치 유형. 계좌번호·금액(가격·평가액)은 넣지 않는다(D-140). 불일치 해소(해소 방법 선택·반영)와 결과 불명 확정은 **로컬 전용을 유지**한다.
- [CP-031] K3(결과 불명 미해소)의 재개와 결과 불명 확정(미접수 종결·접수 채택)은 종전대로 **로컬 전용**이다(변경 없음). CP-031로 M1도 5회 미발견 시 K3가 되므로 이 로컬 절차가 M1·M2 공통의 유일한 해소 경로다. [CP-029] 자동 운영(채널 AUTO)은 K3를 풀지 않는다(알림만).
- 한도·시간 설정은 원격으로 바꿀 수 없다 (§2.3.1).

### 2.10 알림 (R-13, U-04) (Q-E 결정, 2026-10-01)
| 등급 | 사건 | 전달 |
|---|---|---|
| 긴급 | 모든 정지(K1~K8) 발동, 결과 불명, 대조 불일치([CP-025] 새 불일치 항목 또는 프로세스 시작 후 첫 불일치), 위험 축소 요청 거부, 보유 종목 거래정지·상장폐지 예정 | 즉시 |

- 알림 채널: 원격 수단과 같은 메신저 봇 (D-025). 알림이 연속 실패하면 위험 확대를 차단한다 (K11, D-024).
- [CP-025] 대조 불일치 알림은 같은 미해소 항목에 대해 매 대조마다 긴급으로 보내지 않는다(03 D-125). 근거: PAPER-0 1일차에 같은 항목의 긴급 알림이 1분마다 361건 나가 알림 채널 오류 → K11이 발생함(kiwoom-kr §7c, worklog (30)). **K4 발동·유지·재개는 바뀌지 않는다**(알림 횟수만 줄인다).
- [CP-025] 메시지 내용 때문에 텔레그램이 거부한 알림은 등급과 무관하게 다시 보내지 않으며(긴급 포함) 감사 기록·로컬 로그에만 남는다. 긴 알림은 앞 4000자 이내로 잘려 전달된다. 알림은 긴급을 먼저, 나머지는 발생 순서대로 1초 간격으로 보내므로 밀린 알림이 많으면 새 경고·정보 알림이 늦게 도착할 수 있다(A-073 G 정정)(03 D-128·D-130, CP-025 §7.5 R-4·R-5).
- [CP-028] 처리가 취소(저장 단위 롤백)된 작업 중에 난 알림도 사람에게 보낸다: 문구 앞에 "(처리 취소됨)"을 붙여 감사 기록·텔레그램으로 전달한다. 같은 처리가 다시 성공하면 같은 사건 알림이 2건(취소됨 + 정상) 갈 수 있다. 반복 억제(60초)는 실제로 반영된 알림에만 적용된다(03 D-148, A-074 Q-3 B).
- [A-084] **텔레그램 알림에는 금액 원문(원·가격·평가액·예수금)을 넣지 않고 비율(%)로 표시**한다 — 일일 보고 알림(R-26)의 실현·미실현 손익은 일일 기준 금액 대비 %(기준 기록이 없으면 방향만), 체결 알림은 종목·방향·수량만. 03 D-140(`/review`)·D-156(일일 요약)과 같은 정책으로 통일. 금액은 로컬 `status`·일일 보고 파일·paper-review에서 본다.
- [제안] 알림 채널과 원격 명령 채널이 같으므로, 채널 장애 시 원격 킬 스위치도 쓸 수 없다. 대체 수단은 증권사 앱 직접 거래(외부 거래로 처리)뿐임을 운영 절차에 적는다.
