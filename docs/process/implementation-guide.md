# 구현·검토 단계 가이드 (6~7단계)

- 적용: `plan:approved` 게이트가 있고, 사용자가 "구현 시작"을 명시적으로 지시한 뒤
- 상위 규칙: [CLAUDE.md](../../CLAUDE.md). 충돌하면 CLAUDE.md가 우선한다.

## 착수 전 확인
- `docs/approvals.md`에 `plan:approved`와 구현 시작 지시 기록이 있는지 확인한다. 없으면 착수하지 않는다.
- 이번 작업(T-ID)의 선행 조건과 차단 조건이 모두 해소되었는지 확인한다.
- 실전 주문 코드 작성 승인이 없으면 fake 브로커와 PAPER 연동 범위만 구현한다.
- 패키지를 설치하기 전에 목적, 버전, 영향을 설명하고 승인받는다. 의존성은 버전을 고정한다.

## 작업 절차 (T-ID 하나씩)
1. 연결된 요구사항·설계·완료 기준을 확인한다.
2. 해당 동작을 검증하는 테스트를 먼저 작성한다. 정상 경로와 오류 경로를 모두 포함한다.
3. 테스트를 실행해 기대한 이유로 실패하는지 확인한다.
4. 최소한으로 구현한다.
5. 관련 테스트와 회귀 테스트를 실행한다.
6. 보고한다: 변경 파일, 실행한 명령, 결과(통과/실패/건너뜀/미실행 수), 남은 위험
7. 승인된 커밋 정책이 있을 때만 커밋한다.

작업 범위를 벗어나는 리팩터링은 먼저 제안하고 승인받는다.

## 코드 규칙
### 구조
- 전략 계산(순수 함수)을 주문·저장·네트워크 같은 부수효과와 분리한다.
- 모듈 의존 방향은 3단계 설계를 따르고, 자동 검사로 강제한다. 예: 전략이 브로커를 import하면 실패
- 브로커 어댑터는 공통 인터페이스를 구현한다. 시장별 제약은 어댑터 안에 둔다(R-16).
- 주문 관련 호출은 주문 실행기를 통해서만 한다. 주문 실행기는 게이트 승인 결과 없이 호출할 수 없게 만든다(R-03).

### 수치와 시간
- 금액·가격·수량에는 `float`을 쓰지 않는다. `Decimal`처럼 정밀도를 보존하는 타입을 쓴다.
- 반올림 규칙은 시장·필드별로 명시한다.
- 호가 단위, 최소 수량, 수량 단위, 최소 주문 금액은 대상 API의 공식 근거(`docs/broker-specs/`)로 확인한 값만 쓴다.
- 시간대 정보가 없는 시각(naive datetime)은 쓰지 않는다. 저장 기준 시간대는 3단계 설계를 따른다.
- 현재 시각은 주입 가능한 시계 인터페이스로 얻는다. 테스트에서 시간을 제어하고 룩어헤드를 막기 위해서다.

### 스타일
- Python 타입 힌트를 쓰고, 함수는 작게 유지한다.
- 설정은 스키마로 검증하고, 검증에 실패하면 시작을 거부한다(R-19).
- 로그는 구조화된 필드로 남기고, 비밀정보는 마스킹한다(R-11).

## 테스트 규칙
- 테스트 통과만을 위해 테스트를 완화하거나 삭제하지 않는다. 요구사항이 바뀌어 테스트를 고칠 때는 이유와 영향받는 ID를 기록한다.
- 결과는 미실행·실패·건너뜀을 구분해 보고한다.
- 반드시 포함할 시나리오 테스트(업무정의서 E-ID와 연결):
  - 결과 불명, 중복 신호, 재시작 대조, 동시 신호 합산 한도
  - 킬 스위치의 요청 유형별 동작, 모드·환경 불일치
- 테스트에서는 실제 네트워크와 실제 자격정보를 쓰지 않는다. PAPER 연동 테스트는 별도 표시로 분리하고, 사용자 승인 뒤에만 실행한다.

## fake 브로커 → PAPER 순서
1. fake 브로커로 종단 간 흐름과 장애 시나리오(응답 유실, 부분 체결, 거부)를 검증한다.
2. 그다음 모의 환경(M1: 키움 모의투자) 어댑터를 연동한다. 연결 전에 접속 대상과 계좌 유형이 모의임을 확인하는 검사를 둔다.
3. PAPER 자격정보는 사용자가 `.env`에 직접 넣는다. 에이전트는 값을 읽거나 출력하지 않는다.

## 7단계 — PAPER 검토와 LIVE 인계
- 산출물: `docs/07-paper-review.md` (시장별로 작성)
- 포함할 것:
  - 기간, 거래 수, 사용한 전략·설정·코드 버전
  - 백테스트 대비 차이
  - 거부·오류·중복·누락·결과 불명
  - 지연, 체결 차이, 운영 개입
  - 리스크·킬 스위치·복구 검증 결과
  - 충족·미충족·미검증 항목
  - LIVE 차단 조건과 확인 주체
- 실전 전환은 사용자가 주도한다. 에이전트는 승인 범위와 수동 실행·중지·복구 절차를 인계한다.
- 미해결 차단 조건이 있으면 "실전 준비 완료"라고 말하지 않는다.
