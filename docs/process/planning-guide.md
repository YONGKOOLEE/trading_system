# 계획 단계 가이드 (0~5단계)

- 적용: `docs/.status`의 현재 단계가 0~5일 때
- 상위 규칙: [CLAUDE.md](../../CLAUDE.md). 충돌하면 CLAUDE.md가 우선한다.

## 공통 규칙
- `docs/`의 계획 문서만 작성한다. 애플리케이션 코드, 테스트 코드, 의존성 설치, 브로커 연결, 주문 관련 명령은 금지다.
- 공식 문서를 조회하는 웹 검색·열람은 허용된다. API 호출, 로그인, 계정 연결은 금지다.
- 산출물은 [stage-doc-template.md](../templates/stage-doc-template.md) 양식으로 작성한다.
- 산출물 초안을 제시한 뒤 사용자 승인을 받는다. 승인 전에는 다음 단계로 넘어가지 않는다.
- 이 단계의 승인은 구현 승인이 아니다. 5단계가 승인된 뒤에도 사용자가 "구현 시작"을 명시적으로 지시할 때까지 기다린다.

## 다중 시장 처리
- 0~5단계 문서는 **시장 공통 본문**과 **시장별 부록**(M1 국내주식·ETF, M2 크립토, M3 미국주식)으로 나눈다.
- 현재 차수(M1)의 부록만 상세화한다. 다음 차수의 부록에는 알려진 차이와 미확인 항목만 적는다.
- 다음 차수에 착수할 때는 0~5단계 문서 전체를 영향 검토한다. 공통 본문이 바뀌면 이전 차수의 승인과 검증 항목도 재검토한다.
- 시장 간 차이 점검 항목: 거래 시간(24/7 포함), 일일 기준 시각, 통화·환율, 수량 단위(정수 주식 / 소수 코인), 최소 주문 금액, 호가·수량 단위, 수수료·세금, 기업 이벤트, 모의 환경의 한계.

## 0단계 — 전략 정의
- 산출물: `docs/00-strategy.md`, 전략별 문서 `docs/strategies/<전략ID>/`
- 게이트: `strategy:approved`
- 전략 유형이 아직 미정이므로, `00-strategy.md`에는 **전략 정의 형식**을 먼저 정한다. 개별 전략은 `docs/strategies/`에 이 형식으로 추가한다.

`00-strategy.md`에 정할 것:
- 전략 정의 형식: 입력 → 판정 시점 → 조건 → 행동. 수치 조건뿐 아니라 거래 상태·이벤트 조건도 판정할 수 있게 쓴다.
- 등록 명세(R-17): 이름, 버전, 대상 시장, 필요 데이터, 입력 파라미터와 허용 범위(R-19), 신호 출력 형식
- 전략 상태와 전환 조건(R-20). 누가 승인하는지 포함.
- 신호 유효 기간, 복수 신호 우선순위, 같은 종목에 여러 전략의 신호가 겹칠 때의 처리
- 포지션 크기 산정 방식의 틀. 수치는 전략별로 정한다.
- 제외 범위: 레버리지·신용·마진·공매도·파생·선물
- 사람이 하는 종목 선정의 경계. 사람이 만든 목록은 입력으로만 취급한다.
- 전략이 실패할 것으로 예상하는 시장 국면에 대한 가설의 틀

개별 전략 문서(`docs/strategies/<전략ID>/strategy.md`)에 정할 것:
- 대상 시장·종목 범위·보유 기간, 데이터 종류와 신호 평가 시점
- 진입·청산·재진입 조건, 포지션 크기, 실패 국면 가설

## 1단계 — 요구사항과 리스크 정책
- 산출물: `docs/01-requirements.md`
- 게이트: `requirements:approved`
- 업무정의서의 R-ID를 이어받아 상세화한다. 새로 추가하는 항목은 [제안]으로 표시한다.
- 인수 기준은 조건 · 입력 · 기대 결과 · 오류 결과로 쓴다.
- 리스크 수치는 사용자가 정한다. 에이전트는 빈칸과 선택지만 제시한다.
- 손실률에 대해 정의할 것: 분모(평가금액인지 예수금인지), 실현·미실현 손익 포함 여부, 비용(수수료·세금·환전) 포함 여부, 일일 기준 시각(시장별), 기준 통화
- 요청 유형(신규·증액·감액/청산·취소·정정)마다 허용·거부·정지·재개 정책을 정한다.
- 장애 정책: API 단절, 시세 지연, 부분 체결, 응답 유실, 주문 거부, 잔고 불일치, 인증 만료, 호출 제한 초과, 재시작, 시계 오차
- 정지 유형별 승인 표에 넣을 것:
  - 신규 진입·증액 차단
  - 미체결 주문 취소 여부
  - 기존 포지션 유지 또는 감액·청산
  - 불확실한 상태에서 허용할 행동
  - 알림 대상과 사람 확인 필요 여부
  - 재개 조건과 승인 주체
- 운영 관련: 운영 주체, 알림 채널과 알림 실패 시 동작, 원격 킬 스위치 수단, 가용성, 로그·데이터 보존 기간, 백업, 보안 제약

## 2단계 — 범용 데이터 모델
- 산출물: `docs/02-data-model.md`
- 게이트: `data-model:approved`
- 승인된 R-ID만 기준으로 논리 모델을 설계한다. DB 제품별 물리 테이블은 아직 정하지 않는다.
- 다음 개념 사이의 경계를 정한다: 신호, 주문 의도, 전송 시도, 브로커 주문, 체결, 포지션, 리스크 상태·예약 노출, 대조 결과, 운영 요청, 감사 이벤트, 전략 등록·버전
- 엔티티마다 표로 작성한다: 필드, 타입, 필수 여부, 식별자, 관계, 제약, 이력, 삭제, 민감도, 근거 R-ID
- 금액·가격·수량 필드에는 정밀도, 통화, 반올림 규칙을 적는다. 시각 필드에는 시간대를 적는다.
- 상태 전이표와 불변 조건을 정의한다(예: 결과 불명 상태인 의도에는 새 전송 시도를 만들 수 없음).
- 멱등키의 생성 기준, 적용 범위, 보존 기간, 저장 시점(전송 전 영속화)을 정의한다.
- 특정 전략 고유 지표는 핵심 모델과 분리한다.
- 서로 다른 전략 사례 2개에 가상 데이터로 적용해 본다.
- 다음 상황을 처리할 수 있는지 검증한다: 부분 체결, 중복, 응답 유실, 재시작, 외부 수동 거래, 거래정지, 다중 통화
- 요구사항에 없는 요소는 [제안]으로 표시한다. 설계 결정에는 D-ID를 붙인다.

## 3단계 — 시스템 구조와 기술 선택
- 산출물: `docs/03-design.md`, `docs/broker-specs/*.md`
- 게이트: `design:approved`
- 컴포넌트, 책임, 데이터 흐름을 텍스트 도식으로 그린다. 정상 흐름과 실패·복구 흐름을 따로 설명한다.
- 설계할 것: 중앙 주문 통제, 상태 대조, 예약 노출, 킬 스위치, 운영 요청 경로
- 인터페이스 계약과 오류·타임아웃·재시도 정책. 주문 변경 요청에는 자동 재시도를 적용하지 않는다.
- 모듈 의존 방향 규칙과 강제 수단. 예: 전략 패키지가 브로커 패키지를 import하면 검사가 실패하도록 한다(R-02, R-03).
- 인증·권한·비밀 설정·감사·감시·배포·롤백. 자택 PC 기준 프로세스 감시와 재기동 방식도 포함한다(R-18. 자동 실행 등록은 별도 승인).
- 브로커 API 제약 표: 항목, 확인 근거(URL·확인일·버전), 미확인 여부, 차단 여부
- 시장별 시간대·휴장·단축장·동시호가·점검 시간·거래정지/VI. 시각 저장 기준(예: UTC 저장, 시장 현지 시각 병기)
- 기술 선택지는 필요한 항목만 2~3개씩 비교하고, 확인된 환경 조건만 근거로 확정한다(Python 3.14 호환성 포함).
- `src/`·`tests/` 폴더 구조를 이 단계에서 확정한다. 현재 구조는 [제안]이다.
- 결정마다 D-ID를 붙이고 관련 R-ID와 연결한다.

## 4단계 — 검증 계획
- 산출물: `docs/04-validation.md`
- 게이트: `validation:approved`
- 전략 성과와 실행 안전성을 따로 평가한다. 성과가 좋아도 안전성 기준에 못 미치면 전환 불가로 판정한다.

백테스트:
- 데이터 출처·기간·수정 이력·결측 처리
- 신호 발생 시점과 체결 가정
- 룩어헤드·생존편향 검토
- 수수료·세금·슬리피지 가정과 근거
- 학습·검증·최종 평가 구간 분리, 필요하면 walk-forward
- 지표: 수익률, 최대 낙폭, 손익비, 거래 수, 기간별 일관성
- 한계와 과최적화 가능성

실행 안전성:
- 리스크 거부 조건, 동시 요청
- 요청 유형별 킬 스위치 동작
- 주문 거부, 부분 체결, 응답 유실
- 중복 신호, 프로세스 중단, 재시작
- 잔고 불일치, 시세 지연, 인증 만료, 호출 제한, 시계 오차
- 모드·환경 혼용 차단

PAPER:
- 사용자가 승인할 최소 기간, 거래 수, 합격 기준
- 백테스트와 체결 결과의 차이
- 거부·중복·누락·결과 불명·지연·운영 개입
- 모의 환경에서 검증하지 못한 실전과의 차이

LIVE 전환 (시장별):
- 체크리스트 항목별 근거와 통과 여부
- 최초 허용 규모, 중지 조건, 재승인 조건
- 미확인 항목의 차단 여부

각 검증 항목에 대응하는 R-ID와 E-ID를 표로 연결한다.

## 5단계 — 구현 계획
- 산출물: `docs/05-plan.md`
- 게이트: `plan:approved`
- 작업마다 기록할 것: T-ID, 연결 R-ID/D-ID, 선행 조건, 산출물, 정상·오류 검증 방법, 완료 기준, 필요한 권한·가상 데이터·확인 주체
- 첫 작업(T-001)은 최소 종단 간 흐름으로 한다: 가상 입력 → 신호 → 리스크 승인/거부 → fake 브로커 → 결과 기록. 최소 킬 스위치와 주문 차단 검증을 포함한다.
- 그 뒤에는 승인된 의존 관계에 따라 백테스트, 데이터, 상태 대조, 감시, PAPER 연동으로 넓힌다.
- 기한과 인력이 확인되지 않았으면 날짜와 공수를 만들지 않는다.
- 추적표를 작성한다: 모든 핵심 R-ID가 D-ID, T-ID, 검증 항목과 연결되는지 확인하고, 연결되지 않은 항목은 차단 조건으로 표시한다.
- 커밋 정책(시점, 메시지 형식, 브랜치)을 제안하고 승인받는다.
