## 0. 이 문서의 범위
- 3단계 가이드 항목 전체를 다룬다: 컴포넌트·데이터 흐름(정상/실패·복구), 중앙 주문 통제·대조·예약 노출·킬 스위치·운영 요청 경로, 인터페이스 계약과 오류·타임아웃·재시도, 의존 방향 규칙과 강제 수단, 인증·권한·비밀·감사·감시·배포·롤백, 자택 PC 프로세스 감시, 브로커 API 제약 표, 시장 시간·휴장·동시호가·점검·거래정지/VI, 시각 저장 기준, 기술 선택 비교(Python 3.14 호환 포함), `src/`·`tests/` 구조 확정. 각 결정에 D-ID와 R-ID를 붙인다 (§15 점검표).
- **LIVE 실전 주문 코드는 설계하되 작성하지 않는다.** 실전 어댑터 구현은 별도 승인(승인 구조 3번) 대상이다. 이 문서의 승인은 구현 승인이 아니다.
- [v1.0 CP-024] M2(바이낸스 현물 테스트넷) 설계는 2-M2 부록에 둔다. M2의 "구현 시작" 지시, 테스트넷 연결 승인, 실전 주문 코드 승인, LIVE 승인은 각각 별도다(A-066 범위 밖).

## 3. 정상 흐름
1. **시작**: 설정·비밀 로드 → 시작 점검(D-066) → K8 발동 → 토큰 발급 → WS 접속·등록 → 대조(§6.3) → 사용자 재개(01 K8) → 판정 시작.
2. **판정**: 트리거 → Evaluator가 스냅샷(데이터 버전, 설정 버전, 포지션·주문·거래 이력) 구성 → Strategy → 신호 기록(ENT-10·11).
3. **게이트**: 신호가 요청 큐에 들어감 → 게이트가 순서대로 1건씩 G1~G15 판정 → 승인이면 한 트랜잭션으로 판정·의도·예약·소유권·멱등키 기록(INV-03) → 커밋 후 Executor에 전달. 거부면 판정만 기록.
4. **전송**: Executor가 KILL 파일 확인 → 전송 시도 기록(커밋) → 어댑터 호출 → 결과 4분류 반영.
5. **추적**: 00 통보·조회로 접수·체결 반영 → 포지션·소유권 확정·예약 해제(ST-04·05) → 감사 기록.
6. **마감**: 장 마감 후 대조 → 미체결 소멸 확인(K-U3) → 일일 리스크 확정 → 일일 보고 → 백업. [v1.0 CP-024] "장 마감"은 **시장의 일일 마감 시점**이다 — M1은 장 마감 후(위 문장 그대로), M2는 일 경계(UTC 00:00) 직후 대조 1회 → 일일 확정 → 백업이며 마감 미체결 소멸 확인은 없다(D-108·D-109). M2 시작·판정·전송 순서의 차이는 2-M2.2.

### 5.2 전송 결과 4분류 (D-043)
[v1.0 CP-024] 공통 규칙: 판정은 **시장별 매핑 표를 우선**하고, **표에 없는 응답은 결과 불명**으로 본다. HTTP 4xx를 시장 공통으로 일괄 명시 거부로 보지 않는다(D-112). 시장별 매핑: M1 = 2-M1.1(v0.9 §5.2 표 그대로), M2 = 2-M2.5.

| 분류 | 공통 정의 | 의도 상태 |
|---|---|---|
| 전송 전 실패 | 연결 수립 전 오류, 요청 바이트 전송 전 예외, 로컬 검증 실패 | 미전송 종결 |
| 명시 거부 | 응답 수신 + 시장별 매핑 표에서 "미실행"으로 분류된 응답 | 거부 종결 |
| 결과 불명 | 전송 후 타임아웃, 연결 끊김, 5xx, 응답 해석 불가, 시장별 매핑 표에서 결과 불명으로 분류된 응답, **매핑 표에 없는 응답** | 결과 불명 |
| 접수 | 응답 수신 + 시장별 매핑 표의 성공 조건 + 브로커 주문 식별자 있음 | 접수 |
- 성공 응답인데 브로커 주문 식별자가 없으면 결과 불명으로 본다(보수적, 시장 공통).
- [v1.0 CP-024] 매핑 표의 일부를 명시 거부로 옮기려면(PAPER 관찰 근거) CP로 한다.

## 6. 핵심 설계

### 6.1 중앙 주문 통제
- 모든 요청(신호, 운영 요청, 정지 정책 취소, 실행 정책 취소·정정)은 **요청 큐 하나**로 들어가 게이트가 순서대로 판정한다 (D-038).
- 게이트 승인 트랜잭션: `BEGIN IMMEDIATE` → 멱등키 유일 확인 → G1~G15 → 판정·의도·예약·소유권 기록 → `COMMIT`. 커밋 실패 = K7, 전송 없음.
- Executor는 커밋된 의도만 받는다. 코드 경로상 Executor는 게이트 판정 ID 없이 호출될 수 없다(타입으로 강제, §7).

### 6.2 예약 노출 (01 D-017·D-018, 02 ENT-21)
- [v1.0 CP-024] 예약 금액: 지정가는 주문가, 시장가는 시장 부록이 정한 상한 기준 가격으로 계산하고 × |레버리지 배수|. M1: 시장가는 **상한가**(없으면 최근가 × (1 + 가격제한폭)) — 2-M1.2. M2: 매수는 IOC 지정가뿐이므로 예약 = 주문가(D-104).
- 한도 계산 = 포지션 노출(평가액 기준) + 활성 예약. 체결 시 체결분만큼 예약에서 포지션으로 옮긴다. [v1.0 CP-024] IOC 미체결분이 EXPIRED로 끝나면 체결분만 포지션으로 옮기고 남은 예약은 해제한다(M2, D-104).

### 6.5 킬 스위치와 정지 (R-07, D-051)
- 발동 경로: 로컬 `scripts/kill` → DB 명령 테이블 + KILL 파일 생성 / 텔레그램 `/kill` + 확인 코드 → 명령 테이블. 본 프로세스가 명령을 1초 이내에 읽는다.
- KILL 파일은 **본 프로세스와 독립**: Executor가 매 위험 확대 전송 직전에 파일 존재를 확인한다.
- 재개: `scripts/resume <K유형>` 또는 텔레그램(K1·K2만, 01 §2.9). KILL 파일은 로컬에서만 지운다.
- [v0.4 CP-017 T5-7] K7(저장 실패) 운영 절차: 저장소 복구 확인 → 프로세스 재시작 → 시작 대조 → K8 재개. 전송 후 저장에 실패한 실행기는 재시작 전까지 전송하지 않으므로 K7 재개만으로는 주문이 재개되지 않는다.
- 본 프로세스가 죽어 있으면 주문도 없다. 이때는 증권사 앱이 유일한 수단이며 외부 거래로 처리된다(01 §2.10).

### 6.6 운영 요청 경로 (R-21)
```
로컬 CLI ──┐
           ├─▶ DB 명령 테이블(명령 ID = 멱등키) ─▶ OpsCommand: 인증·원격 허용 검사 ─▶ 요청 큐 ─▶ 게이트
텔레그램 ──┘   (채널 메시지 ID = 멱등키)
```
- 로컬 CLI 인증: Windows 로그인 사용자 = 운영자(단일 사용자 가정). 텔레그램 인증: 허용 채팅 ID + 1회용 확인 코드(60초 유효).
- 명령 결과는 같은 채널로 회신한다.
- [v1.0 CP-024] `/exit`·`/reduce`의 수량은 **그 시장의 수량 단위**에 따라 해석한다: 수량 단위가 소수인 시장(M2)만 소수를 허용하고, M1은 정수만 계속 허용한다(공통 코드 변경, M1 회귀 대상, D-117). 텔레그램 봇은 시장별이며 M2 메시지 앞에 `[M2]`를 붙인다. M1 메시지의 `[M1]` 표시는 T-M2-13에서 함께 넣는다(A-065 Q5).
- [v0.9 CP-023] 시작 시각보다 2분 넘게 오래된 텔레그램 메시지(꺼져 있던 동안 보낸 것)는 `/kill` 포함 실행하지 않고, 다시 보내라고 회신하며 감사 REMOTE_STALE을 남긴다. 메시지 시각이 없으면 오래된 것으로 보지 않는다.
- [CP-025] 수신 처리 실패(D-131): 명령 처리 중 저장 실패면 offset을 넘기지 않아 다음 폴링에서 같은 메시지를 다시 처리한다(멱등키 = 채널 메시지 ID라 접수는 1회). 같은 메시지가 3회 연속 저장 실패면 건너뛰고, 허용 채팅에 "접수하지 않음 — 긴급 정지는 PC에서 kill.py" 직접 회신 + 경고 알림(저장소 경유라 닿지 않을 수 있음). 저장 실패가 아닌 예외는 건너뛰고 기록, 형식이 잘못된 update는 무시. 실패 횟수는 메모리에만 있다.
- [CP-025] 확인 코드(D-132): 접수(저장) 성공 뒤에 소비한다. 저장 실패 후 재처리가 60초 유효 안이면 같은 코드로 접수된다. 오류·만료·다른 채팅은 거부 시 소비.

- gate·execution은 구체 저장소(`storage.repository`)를 쓴다. 저장소 인터페이스 분리는 하지 않는다(단일 SQLite 구현).

- Executor 입력 타입은 `ApprovedIntent`(게이트만 생성 가능한 타입)로 한정한다.
- [v1.0 CP-024] 바이낸스 전용 요청·응답·규칙 타입은 `broker/binance/` 안에만 둔다. 공통 계약(§5.1)으로의 연결은 일반화 작업(T-M2-03~05)에서 한다(D-119).

## 9. 배포·롤백·백업 (D-060, R-25)
- 실행 단위: Git 태그(`vX.Y.Z`)를 체크아웃한 디렉터리 + 전용 가상환경. 실행 시 태그·커밋·설정 해시를 감사에 기록.
- 의존성: 6단계에서 설치 승인 후 `requirements.txt`(해시 포함)로 고정.
- 마이그레이션: `storage/migrations/NNN_*.sql`, 전진 전용. 적용 전 자동 백업.
- 백업: 매일 장 마감 후 `sqlite3` 백업 API로 `var/<mode>/backup/`, 7일 보관(01 §2.12). 외부 저장소 복사는 [제안] 사용자 결정. [v1.0 CP-024] "장 마감 후"는 시장의 일일 마감 시점이다 — M1 장 마감 후, M2 일 경계(UTC 00:00) 직후 일일 확정 뒤(D-108·D-109). 경로는 각 체크아웃의 `var/<mode>/backup/`.
- [v1.0 CP-024] 스키마를 바꾸는 M2 작업(T-M2-04·05·06·08)은 M1 DB 마이그레이션이 필요하며, M1 PAPER-1 중간에는 넣지 않는다. 적용 전 백업(D-060).
- 복원 시험: `scripts/restore-test`가 백업을 임시 위치에 복원 → `PRAGMA integrity_check` → 감사 순번 연속 확인. PAPER 시작 전 1회, 이후 분기 1회.
- 롤백: 프로세스 정지(K1) → 이전 태그 체크아웃 → 스키마가 바뀌었으면 백업 복원 → 시작(K8) → 대조 → 사용자 재개.

### 2-M1.1 전송 결과 매핑 (키움, v0.9 §5.2 표) [v1.0 CP-024 이동]
| 분류 | 판정 조건 | 의도 상태 |
|---|---|---|
| 전송 전 실패 | 연결 수립 전 오류, 요청 바이트 전송 전 예외, 로컬 검증 실패 | 미전송 종결 |
| 명시 거부 | 응답 수신 + `return_code` ≠ 0 (단, 1999 제외) 또는 HTTP 4xx 응답 본문 수신 | 거부 종결 |
| 결과 불명 | 전송 후 타임아웃, 연결 끊김, HTTP 5xx, 응답 해석 불가, `return_code` 1999 | 결과 불명 |
| 접수 | 응답 수신 + `return_code` = 0 + 주문번호 있음 | 접수 |
- `return_code` = 0인데 주문번호가 없으면 결과 불명으로 본다(보수적).
- 실제 오류 응답 형태는 PV-01에서 검증한다 (K-U7).
- (§5.2 공통 규칙 "표에 없으면 결과 불명"과의 관계: M1은 위 표를 그대로 적용한다. 위 표는 "응답 해석 불가 = 결과 불명"을 이미 포함하므로 M1 동작 변화는 없을 것으로 보나, 구현 시 M1 분류 코드가 위 표 밖의 응답을 다르게 처리하는지 M1 회귀 시험으로 확인한다 [추정].)

### 2-M2.2 정상 흐름 (CP-024 §2.2)
1. 시작: 모드·market·broker·도메인·DB 메타 일치(D-097·D-098) → 바이낸스 서버 시각(D-115) → exchangeInfo(규칙·rateLimits, D-106·D-113) → 계좌 조회 → 대조(D-103·D-109) → K8 재개 대기(M1과 같음).
2. 판정: 일 경계 뒤 1d 봉 확정(D-108) → 전략 신호 → 게이트(G1~G15, G10 = 거래 규칙, G11 = 시세 신선도, G12 = 24/7 + 주문 창).

4. 전송: 고객 주문 ID(D-110) 포함 IOC 지정가 매수 또는 시장가 매도(시세 지연 중 감액·청산은 IOC 지정가 매도, D-120) → 4분류(2-M2.5).

6. 대조: 주기 60초, 자산별 수량 + USDT(D-103·D-118). 사용자 스트림 재연결 후, 일 경계(UTC 00:00 직후) 1회 — 일일 확정·백업(D-109).

### 2-M2.4 주문 식별·결과 불명 해소 (D-110·D-111)
- 고객 주문 ID: 멱등키에서 결정적으로 생성, 1~36자 `[A-Za-z0-9_-]`, 의도별 유일, 재사용 금지, 재시작 후 같은 의도는 같은 ID. 서버 중복 거부는 멱등성이 아니다.
- 브로커 주문 식별 = (계좌, 심볼, orderId) + 고객 주문 ID. 거래일을 식별에 쓰지 않는다(M1 D-046과 다름).
- 해소: 회차·간격은 공통(5회, 2·4·8·16·32초). 조회 키 = orderId(있으면, 심볼과 함께) / 없으면 origClientOrderId. -2013이면 같은 회차에 allOrders·myTrades(심볼, 전송 시각 전후 24시간 창 이내) 교차 확인. 5회 모두 없음 → K3, 자동 미접수 종결 없음. 전송 90일 이내 주문의 -2026 → K3.
- 보류 기간(§6.3 CP-022 문단·resolver의 경과 기준) = **전송 후 24시간 이내**. 넘으면 K3. 완화는 PV-M2-02 실측 뒤 CP.

### 2-M2.6 주문 유형·수량·현금·정밀도 (D-101~D-104·D-106·D-118·D-120, CP-024 §2.5)
- 주문 유형: 매수 = IOC 지정가(최근가 × 1.005, tickSize 내림, 예약 = 주문가). 매도 = 수량 지정 시장가. 시세 지연 중 감액·청산 = IOC 지정가 매도(마지막 정상 시세 × 0.995, tickSize 올림) — 유형·가격은 의도 생성 시(게이트 전) 정하고 게이트는 바꾸지 않는다. 정정 미지원, 취소 지원. newOrderRespType = FULL, quoteOrderQty 미사용.
- 거래 규칙: 심볼별 규칙 값 객체(MarketFacts), 시작 점검·일 경계 적재. 매수는 보수(주문가 기준, 경계면 거부), 매도는 확실한 위반만 거부. 시장가 수량 = MARKET_LOT_SIZE, 지정가 = LOT_SIZE.
- 수량: 포지션 = 순 수령(D-101). dust는 실제로 보낼 매도 경로의 필터로 판정(D-102) — 확정 시 포지션 없음 취급·소유권 해제·L6 제외·알림, 원장·대조에는 유지.
- 현금: 키움 T+2 보수 차감(ConservativeCashFacts)은 M2에 쓰지 않는다 — 바이낸스 잔고는 체결 즉시 반영되어 이중 차감이 된다[추정, 조사 #17]. 주문 가능 USDT = min(거래소 USDT free, 내부 기대 USDT − 활성 매수 예약 − 추정 수수료(D-118 올림)).
- 대조 범위: 유니버스 기초 자산 + USDT, free + locked, 기대 USDT = 기준선 + Σ(매도 수령액 − 매수 지급액 − USDT 수수료), 차이 ≠ 0 → K4. 범위 밖 자산은 시작·일 경계 스냅샷, 변화는 정보 알림(D-103).
- 정밀도: Decimal, 고정소수 문자열(지수 표기 없음), 수량 내림. USDT 현금 흐름은 거래소 보고 금액(executionReport `Y` 또는 myTrades `quoteQty`)으로 확정, fills만 있으면 price × qty 임시값. `cummulativeQuoteQty` < 0 = 데이터 없음. 비용 추정은 quoteAssetPrecision 올림. M1 정수 올림 규칙은 M1에만(D-118).
- 한도·시간 설정 값(L1~L10, 완충, 신선도, 주문 창 등)은 01 2-M2와 `config/m2/limits.paper.toml`이 정한다(A-064).
